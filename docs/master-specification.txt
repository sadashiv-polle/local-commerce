Multi-Shop Commerce, Delivery, Marketplace Payments & ERPNext Platform

Build a production-ready, secure, cloud-deployable multi-shop local commerce, delivery, marketplace payment and ERPNext integration platform.

The platform must support multiple independent local businesses operating from a single Frappe/ERPNext installation while maintaining strict shop/company data isolation.

The initial business use case is a fish shop, but the architecture must be completely generic and must support:

Fish shops

Meat shops

Grocery stores

Restaurants

Fast-food businesses

Bakeries

Pharmacies where legally appropriate

Local retailers

Other small and medium local businesses

The application must be configuration-driven, API-first, permission-aware and extensible.

0\. NON-NEGOTIABLE FRAPPE CUSTOM APP AND GIT REPOSITORY REQUIREMENT

This project must be built as a real, installable Frappe custom application—not as a generic Python project, standalone Vue project, mock-up, code sample, architecture document or collection of disconnected files.

The final repository must follow the standard structure and conventions produced by `bench new-app` and must be directly compatible with a normal Frappe Bench installation.

Use these canonical identifiers consistently unless I explicitly change them before development begins:

App/repository name: `local_commerce`

Python package name: `local_commerce`

Frappe module name: `Local Commerce`

Custom DocType prefix: `LC`

The app name must use lowercase snake_case, must not contain spaces or hyphens, and must be identical in `hooks.py`, `modules.txt`, `pyproject.toml`, package imports, build configuration and installation commands.

Target Frappe and ERPNext version 15. Do not use APIs that are exclusive to later versions unless they are protected by a documented compatibility layer.

If a working Bench environment is available, first generate the base app using:

`bench new-app local_commerce`

Then implement the project inside that generated app. If Bench is not available in the development environment, reproduce the same valid Frappe v15 app scaffold exactly. Do not invent a custom framework layout.

The Git repository root must be the app root—the directory containing `pyproject.toml`, `README.md`, `license.txt`, `package.json` where required, and the inner `local_commerce` Python package. Do not wrap the app in an unnecessary extra parent project directory.

This tree is a baseline, not permission to create empty placeholder folders. Include the standard scaffold files and add only the directories required by the implementation. Every Frappe module and DocType directory that Python imports must contain the necessary `__init__.py` file.

All custom DocTypes must be developer-mode files committed to Git. Each DocType must have its standard JSON definition, Python controller, tests and optional JavaScript controller in the canonical Frappe module path. Do not create essential schema manually in production through Desk and do not depend on uncommitted database-only customization.

Any required Custom Fields, Property Setters, Roles, Role Profiles, Workflows, Notifications, Print Formats, Workspace records or other configuration records must be reproducible after installation. Store them using the correct Frappe mechanism: standard app records, fixtures declared in `hooks.py`, install/migrate hooks, or idempotent patches. Never require manual recreation on every server.

All patches must be idempotent, listed in `patches.txt`, safe to run through `bench migrate`, and covered by tests when they change business data. Never edit ERPNext core files, Frappe core files, or another app's source code. Extend them only through documented hooks, overrides used sparingly, custom fields, events, APIs and fixtures.

The Vue 3 interface must live inside the same Git repository and the same Frappe app. `frontend/` contains the Vue source. Its production build must output versioned assets into `local_commerce/public/frontend` or another documented Frappe-served app asset directory. Configure Vite base paths, routing and asset URLs so the production UI works when served by Frappe—not only from the Vite development server.

Do not create a second backend, separate Node/Express API, separate authentication database or independently deployed frontend. Frappe is the backend, authentication layer, permission engine and API host. Node tooling may be used only to build the Vue frontend.

Use Frappe session authentication, CSRF protection, whitelisted methods, permission checks, background jobs, realtime events and site configuration correctly. Never import Bench or site-specific paths into application code. Never hard-code a bench path, site name, domain, server IP, Redis URL, database credentials or production secret in the repository.
